# Addon packaging, distribution & updates

How the **OmnibusCloud Render Bridge** Blender addon is built, shipped, installed, and updated.
Companion to `addon-production-readiness.md` (feature backlog) and the addon `README.md` (dev notes).

---

## 1. How Blender addons are distributed (background)

There are two models; this addon uses the modern one.

- **Legacy add-on** (pre-4.2): a `bl_info` dict in `__init__.py`, installed via *Preferences → Add-ons →
  Install from Disk* (a `.zip`). **No built-in updates** — historically people bundled a 3rd-party
  "Addon Updater". Still works in 4.2+ but deprecated.
- **Extension** (Blender **4.2 LTS+**, 2024+): a `blender_manifest.toml` next to the code, packaged as a
  `.zip`. Distributed via either:
  - **extensions.blender.org** — the official public listing. Review process; intended for free,
    open community add-ons; bundled non-Python binaries and large blobs are restricted. **Not** the right
    channel for a commercial add-on that ships a platform-specific C# bridge.
  - **Self-hosted remote repository** — a directory served over HTTPS containing the extension `.zip`s
    plus an `index.json` (generated by `blender --command extension server-generate`). The user adds the
    repo URL once in *Preferences → Get Extensions → Repositories*; Blender then offers **one-click
    install and automatic update checks**. ← **this is our path.**

This addon already ships `outwit_render_bridge/blender_manifest.toml` (schema 1.0.0, `type="add-on"`,
`blender_version_min="4.0.0"`), so the self-hosted-repo path with auto-update is available; we just need
to host the repo and tag platforms.

> Note: `blender_version_min` is `4.0.0`, but the **extension** repo/auto-update mechanics require the
> user to run **Blender 4.2+**. On 4.0–4.1 the same zip still installs as a legacy add-on (no auto-update).

## 2. This addon is platform-specific (it bundles the bridge)

The addon launches a **C# bridge** (`OutWit.Render.BlenderBridge`, .NET 10). `bridge_launcher.py` looks
for the bridge binary bundled under `outwit_render_bridge/bridge/<rid>/{self-contained|framework-dependent}/`
(falling back to a configured `bridge_executable_path` preference or a dev build). So a package is built
**per platform**:

| .NET RID | Blender platform tag | Notes |
|---|---|---|
| `win-x64` | `windows-x64` | |
| `linux-x64` | `linux-x64` | |
| `osx-arm64` | `macos-arm64` | Apple Silicon |
| *(osx-x64, win-arm64, linux-arm64)* | *(macos-x64, …)* | not built yet — add if demand |

Two deployment modes per platform:
- **self-contained** (single-file, bundles the .NET runtime) — **ship this to artists**; zero prerequisites.
- **framework-dependent** (`.dll`, needs .NET 10 installed) — smaller; for advanced/controlled environments.

## 3. Current build pipeline (what exists today)

- `Build-BlenderAddonPackage.ps1` — builds ONE variant: `-RuntimeIdentifier <rid> -DeploymentMode
  {SelfContained|FrameworkDependent}`. It `dotnet publish`es the bridge for that RID, stages it under
  `outwit_render_bridge/bridge/<rid>/…`, and zips the addon to
  `dist/omnibuscloud-render-bridge-blender-addon-<rid>-{selfcontained|dotnet}-<version>.zip`.
- `Build-BlenderAddonPackages.ps1` — master: builds all **6** variants (3 platforms × 2 modes).
- Version is read from `bl_info` in `__init__.py`.
- **All manual.** No CI. No extension-repo index. No auto-update.

## 4. Production pipeline (target)

1. **Version bump** — single source of truth. Today version lives in BOTH `__init__.py` `bl_info` and
   `blender_manifest.toml`; they must match. Bump both (add a CI check that they agree).
2. **CI build on tag** (`addon-v*`): GitHub Actions runs the master build (pwsh + .NET 10), producing the
   per-platform zips. See `.github/workflows/addon.yml`.
3. **Validate**: `blender --command extension validate <zip>` to catch manifest errors before publishing.
4. **Publish**:
   - Attach the per-platform **self-contained** zips to the GitHub Release (offline-install artifacts).
   - Regenerate the extension repo `index.json` (`blender --command extension server-generate
     --repo-dir <dir>`) over the published zips and upload `index.json` + zips to the HTTPS host.
5. **Host the repo** at a stable URL, e.g. `https://omnibuscloud.com/blender/index.json` (static hosting /
   bucket / GitHub Pages). This URL is what users add to Blender.

### Decisions (2026-06-06)
- **Final host = the crowdcomputing portal (omnibuscloud.com).** The extension repository
  (`index.json` + zips) will live there once the portal ships. Until then, see "Temporary
  distribution" below.
- **Platform tagging: DONE.** `Build-BlenderAddonPackage.ps1` now stamps `platforms = ["<tag>"]` into
  each zip's manifest (win-x64→windows-x64, linux-x64→linux-x64, osx-arm64→macos-arm64). The future repo
  serves the right zip per OS, and install-from-disk refuses a wrong-arch package.
- **Version sync: DONE.** The build fails if `__init__.py` `bl_info` version ≠ `blender_manifest.toml`
  version. Bump both together (single version, two files).
- **Platform matrix = win-x64, linux-x64, macos-arm64 (Apple Silicon).** No Intel mac (Blender 5+ drops
  it); add arm Linux/Windows only on demand.

**Still open (needs the portal / infra):**
- [ ] Host the repo `index.json` + zips over HTTPS (portal, or a temporary host — below).
- [ ] CI step to regenerate (`blender --command extension server-generate`) + upload the repo index.

### Temporary distribution (now, while the portal is not ready)
For debugging, use **install-from-disk** — no infra:
1. Get a zip for your OS: run `OutWit.Render.BlenderAddon/Build-BlenderAddonPackages.ps1` locally, or push
   an `addon-v*` tag and grab the per-platform zips CI attaches to the GitHub Release.
2. *Preferences → Get Extensions → ▾ → Install from Disk* (4.2+) → pick the **self-contained** zip → enable.
3. To iterate: rebuild and install again.

Optional temporary auto-update repo (if you want to test the in-Blender update flow before the portal):
publish the zips + a generated `index.json` to a static HTTPS location (e.g. GitHub Pages →
`https://omnibuscloud.github.io/Blender/index.json`) and add that URL as a remote repository. Migrating to
the portal later is just changing the publish target + the URL users add.

## 5. End-user guide

### Recommended: install via the OmnibusCloud extension repository (gets updates) — Blender 4.2+
1. *Edit → Preferences → Get Extensions*.
2. Top-right *Repositories* (dropdown) → **+** → **Add Remote Repository**.
3. URL: `https://omnibuscloud.com/blender/index.json` *(final URL TBD — see §4)*. Enable *Check for
   Updates on Startup* if you want automatic update prompts.
4. Back in *Get Extensions*, search **OmnibusCloud Render Bridge** → **Install**. Blender picks the right
   build for your OS automatically.
5. **Updates**: Blender checks the repo and shows an update; or *Get Extensions → ⟳ Check for Updates*.

### Fallback: install from disk (offline, no auto-update)
1. Download the zip for your OS from the GitHub Release (pick the **self-contained** one):
   `…-win-x64-selfcontained-…zip` / `…-linux-x64-…` / `…-osx-arm64-…`.
2. *Edit → Preferences → Add-ons* (4.0–4.1) or *Get Extensions → ▾ → Install from Disk* (4.2+) → select
   the zip → enable **OmnibusCloud Render Bridge**.
3. To update: download the newer zip and install it again.

### Prerequisites
- **self-contained** build: none.
- **framework-dependent** build: the **.NET 10 runtime** installed.
- Blender **4.2+** for the repository/auto-update flow (4.0+ for plain install).

### First run
The addon bundles and auto-launches the bridge (a local process). Open the *OmnibusCloud* sidebar tab in
the 3D View → sign in (browser/OIDC) → pick a **Target** (All clients or a group) → **Start**.

---

## 6. Maintainer release checklist
1. Bump version in `__init__.py` `bl_info` **and** `blender_manifest.toml` (keep them equal).
2. Push tag `addon-v<version>` → CI builds the per-platform zips (validate + build).
3. Verify CI attached the self-contained zips to the Release.
4. Regenerate the repo `index.json` over the new zips and publish to the HTTPS host (until the CI step
   exists, run `blender --command extension server-generate` locally).
5. Smoke-test: in a clean Blender 4.2+, add the repo URL, install, sign in, render a frame on a group.
